# 下一步評估：向量檢索、2.5D／雙向上下文、論文路線（2026-11-08）

## 現況（評估的出發點）

- 單字：YouTube 單字影片第一個詞 72%；連續對話精確 3.7%、召回 2.7%（基準 1.1% / 0.4%）。
- contextbench：理想上下文精確只到 6.1%，模型輸出當上下文沒幫助。瓶頸在「連續手語裡的單一手勢認不出來」，不是缺語意。
- 模型只用 x、y（`ml/wlasl/model.py` 開頭註解），z 有存在 .npy 裡但沒用。

## 1. 向量資料庫存姿勢＋意思、用檢索選中

**結論：對目前的瓶頸不會更好。**

- 檢索 = 用某個 embedding 做最近鄰。最近鄰的品質完全取決於 embedding；用同一個模型的 embedding 做 kNN，效果大致等同現在的分類頭，不會更好。
- 問題在單字（乾淨、有起訖）和連續（協同發音、沒有停頓）之間的領域落差。存再多單字範本，連續片段的 embedding 一樣離它們很遠。
- 文獻佐證：SignMatch（arXiv 2609.01886，2026-09）做的正是「字典範本 ↔ 連續影片」的嵌入比對，但它的 embedding 是**用有標註的連續影片學出來的**，才能匹配。關鍵是訓練資料，不是檢索機制。
- 規模上 2000 類用 numpy 暴力算就夠，不需要向量資料庫。

**它真正有用的地方（之後可以做）**：不重訓就加新詞（錄幾支範本即可）、用距離拒絕詞彙表外的手勢、讓使用者錄自己的版本做個人校準。

## 2. 2.5D ＋ 看前後語意的架構

### 2a. 2.5D（加入 z 相對深度）

- 成本低：資料已經有 z，只要改 `build_features` 重訓一次做對照。
- 預期：可能對手形相近的單字小幅有幫助，但 MediaPipe 的 z 雜訊大（當初就是因此拿掉）。對連續 3.7% 這個數字幾乎不會有影響。**這是假設，沒量過。**

### 2b. 會看前後的架構（雙向時序模型＋CTC）

- 方向正確：這就是連續手語辨識（CSLR）的標準做法，讓模型在協同發音的情境下學會切分與辨識。
- 但**沒有連續資料就訓練不起來**。WLASL 全是單字影片；我們合成的「串接單字」已經試過（召回 59%→49%），真實對話仍然失效，代表合成的串接無法模擬真實的協同發音。
- 事後加語言模型（LLM 重排）已證明無效（理想上下文也只有 6.1%）。上下文必須在視覺模型內部學，而不是事後補。

**結論：兩者單獨都不實用；2b 只要有連續標註資料就是正解。**

## 3. 論文與資料路線（agent-reach 搜尋結果）

## 建議路線（由小到大）

1. **A：ASLLRP 連續語料切出的單字微調**（建議先做）。用真實協同發音樣本微調現行分類器與窗口偵測，直接攻擊領域落差，架構不用改。驗收：podcast／YouTube 對話精確與召回（現行 3.7% / 2.7%）。需要先確認 ASLLRP 的授權與下載方式。
2. **B：同一份語料的句子 gloss 序列做 CTC 連續模型**（雙向 Transformer＋CTC）。這就是第 2b 點，資料到手後才可行。
3. **C：SignMatch 式嵌入＋向量檢索**，用來擴充詞彙與拒絕詞彙表外的手勢（第 1 點的正確版本）。
4. 暫不做：How2Sign／YouTube-ASL 的 gloss-free 翻譯（運算量大、文獻品質仍低）；2.5D 可順手在 A 的重訓裡加一組對照。
